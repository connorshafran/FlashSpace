### D. Fix #3: Simplified App Assignment Model (PARTIALLY WORKING - HAS BUGS)

The original Fix #3 involved complex minimize/un-minimize detection. User rejected it as too complex and unreliable. It was replaced with a simpler "borrow" model:

#### The Borrow Model

- **Borrowed apps** are apps temporarily visible on a non-home workspace. They auto-clean when the user returns to the app's home workspace.
- **Applies to BOTH perm and temp apps** (same behavior for both).
- **"Switch workspace on app focus" ON**: should navigate to the app's assigned workspace, never borrow.
- **"Switch workspace on app focus" OFF**: should borrow the app to the current workspace.
- **Space Control drag-drop** is the deliberate way to move apps between workspaces.

#### Logic in `FocusedWindowTracker.temporarilyAssignAppIfNeeded()` (line 164):

```
1. If app is unassigned → temp assign to current workspace (existing behavior)
2. If app is on its home workspace → remove any stale borrow state
3. If app is temp-assigned + isolation mode + was on secondary display → move temp assignment (drag-back)
4. If "switch on focus" is ON → return (let activeApplicationChanged handle it)
5. If "switch on focus" is OFF → borrow the app
```

## Outstanding Bugs

### Bug 1: Temp Apps Don't Return When Borrowed (affects both ON and OFF)

**Symptom:** When a temporarily-assigned app is "borrowed" to another workspace, it sticks there permanently instead of returning to its home workspace when the user switches back. Permanent apps DO return correctly.

**Expected:** Temp apps should behave identically to perm apps for borrowing - they get borrowed, and when the user returns to the app's home workspace, `cleanUpBorrowsOnReturn()` pulls them back.

**Where to investigate:**

The `cleanUpBorrowsOnReturn(to:)` method (line 870) should handle this:
```swift
private func cleanUpBorrowsOnReturn(to workspace: Workspace) {
    let homeApps = workspace.apps + (temporaryApps[workspace.id] ?? [])
    for app in homeApps { ... }
}
```

The `showApps()` method (line 195) has suppression logic that may interfere:
```swift
let movedAway = temporaryApps.filter { $0.key != workspace.id }
    .values.flatMap { $0 }.map(\.bundleIdentifier)
let borrowedAway = borrowedApps.filter { $0.key != workspace.id }
    .values.flatMap { $0 }.map(\.bundleIdentifier)
let suppressedBundleIds = Set(movedAway + borrowedAway)
```

**Potential root cause:** The `suppressedBundleIds` in `showApps()` suppress apps that are borrowed to ANY other workspace BEFORE checking workspace membership. Even if `cleanUpBorrowsOnReturn()` cleans up correctly, there might be a timing or ordering issue. Also check whether `borrowedAway` should exclude apps that are HOME on the current workspace (i.e., don't suppress an app on its home WS just because it was also borrowed elsewhere).

Another potential issue: When a temp app is borrowed to WS2 and the user focuses it there, the `temporarilyAssignAppIfNeeded` logic might inadvertently modify the temp assignment instead of just borrowing.

### Bug 2.1: Temp Apps Don't Trigger Workspace Switch When "Switch on Focus" is ON

**Symptom:** With "switch workspace on app focus" ON, focusing a permanently-assigned app correctly switches to its workspace. But focusing a temporarily-assigned app does NOT switch - the app just stays on the current workspace.

**Expected:** Focusing a temp-assigned app should switch to the workspace where it's temp-assigned, same as perm apps.

**Where to investigate:**

`FocusedWindowTracker.activeApplicationChanged()` (line 79):
```swift
let shouldActivate = workspaceSettings.activeWorkspaceOnFocusChange &&
    (!workspaceSettings.autoAssignAppsToWorkspaces || !workspaceSettings.autoAssignAlreadyAssignedApps)
```

If `autoAssignAppsToWorkspaces` is ON and `autoAssignAlreadyAssignedApps` is ON, `shouldActivate` is false, causing the method to return early (line 85). This would prevent workspace switching for ALL apps, not just temp ones. Check the user's settings combination.

Also check that the workspace lookup (line 104-110) correctly finds temp-assigned workspaces:
```swift
let workspace: Workspace? =
    workspaceRepository.workspaces.first(where: {
        workspaceManager.isTemporaryApp(app.toMacApp, in: $0.id)
    }) ??
    (activeWorkspaces + workspaceRepository.workspaces).first(where: {
        $0.apps.containsApp(app)
    })
```

This iterates `workspaceRepository.workspaces` and checks `isTemporaryApp`. The temp app should be found. But if the lookup returns `nil` (e.g., the workspace was removed), the guard at line 111 would exit early.

### Bug 2.2: Apps on Extended Display Shouldn't Snap Back on Focus

**Symptom:** If an app (perm or temp) is moved to an extended display (by dragging its window), then focusing that app from the main display causes a workspace switch back to the app's assigned workspace. The user wants apps on external displays to be "separated" from their workspace - focusing them should NOT cause any workspace movement.

**Expected:** Once an app is on another display (physically moved by the user), clicking on it should NOT trigger workspace switching. It's been "separated" from its workspace by being on a different display.

**Where to investigate:**

This requires detecting whether the focused app's window is on a different display than the workspace's assigned display. The check should go in `activeApplicationChanged()` - before switching workspaces, check if the app's current display matches the workspace's display. If the app is on a different display, skip the switch.

Relevant API: `app.display` gives the app's current display. `workspace.displays` gives the workspace's assigned displays. If `app.display` is NOT in `workspace.displays`, the app has been "separated" and focusing it should be a no-op (or a borrow).

This may also need changes in `temporarilyAssignAppIfNeeded()` for the "switch OFF" case - if the app is on a different display, it might need special handling.

### Bug 3: Space Control Drag-Drop Feature Mostly Non-Functional

Three sub-issues:

#### 3a. Left-clicking a workspace tile no longer works

**Symptom:** Tapping a workspace thumbnail doesn't navigate to that workspace anymore.

**Root cause:** The `.ifTrue(dragDropEnabled)` modifier wraps the tile with `.onRightClick()` and `.dropDestination()`. The `onRightClick` overlay (`RightClickOverlay`) uses an `NSView` overlay that may be intercepting ALL mouse events, not just right-clicks. The `RightClickNSView` only overrides `rightMouseDown`, but the NSView itself might be eating left-click events that SwiftUI's `.onTapGesture` expects.

**Where to fix:** In `View.swift`, the `RightClickNSView` (line 72) might need to pass through left-click events. Consider:
- Not using an overlay approach - instead use `.contextMenu` or a gesture-based approach
- Making the NSView transparent to left-clicks by not consuming them
- Alternatively, use SwiftUI's native `.onTapGesture` with button mask, or use `NSClickGestureRecognizer` with `buttonMask = 0x2` (right button)

Actually the issue is more likely that `.onTapGesture` is on the parent view but the overlay is catching clicks. The `.onTapGesture { viewModel.onWorkspaceTap(workspace) }` is at line 95 of `SpaceControlView.swift`, applied BEFORE the `.ifTrue(dragDropEnabled)` modifier. The right-click overlay's NSView sits on top and may block the tap gesture.

#### 3b. Popup is insanely wide (full screen width)

**Symptom:** The right-click popup menu spans the full screen width.

**Root cause:** The popup is positioned using `.position(position)` which sets the CENTER of the view. The popup's width is unconstrained - it uses `.frame(minWidth: 180)` with no max. But the real issue is likely that the popup is inside a `ZStack` that fills the entire screen (`frame(maxWidth: .infinity, maxHeight: .infinity)`), and the popup's `VStack` is stretching to fill. Also, the `Spacer()` inside each `HStack` row (line 44 of `SpaceControlAppListPopup.swift`) pushes the row to fill available width.

**Where to fix:**
- Add `.fixedSize()` to the popup's outer container so it sizes to fit content rather than stretching
- Or add `.frame(maxWidth: 300)` or similar constraint
- The `.position()` modifier itself can cause sizing issues in SwiftUI - it sizes the view to fill the parent first, THEN positions it. Consider using `.offset()` instead, or wrapping in a `GeometryReader`

#### 3c. Can't drag items from the popup

**Symptom:** Items in the popup list can't be dragged to workspace tiles.

**Root cause:** Multiple potential issues:
1. The `.draggable(item)` modifier on the popup rows may conflict with the dismiss backdrop (`Color.clear.contentShape(Rectangle()).onTapGesture`)
2. The popup is in a ZStack layer above the workspace tiles, so drag gestures starting on the popup may not be able to target the `.dropDestination` on the tiles underneath
3. SwiftUI's drag-and-drop between different layers of a ZStack can be unreliable
4. The `Transferable` conformance uses `.json` content type, but `.dropDestination` expects it to match - verify the types align

**Architectural consideration:** The current approach puts the popup and drop targets in the same ZStack. A better approach might be:
- Use a SwiftUI `.popover` or `NSPopover` for the app list (separate window layer)
- Use `NSPasteboard` / `NSDraggingSource` directly for more reliable drag behavior
- Or restructure so the popup is in a separate overlay window
